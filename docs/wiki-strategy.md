# Wiki 胜负题复盘与决策策略对照

## 基线复盘

40 道配对题中，有 Wiki 组独赢 5 题，无 Wiki 组独赢 3 题。下表列出失分以及工具记录能支持的解释。工具次数以逐题报告为准。

| 题目 | 获胜组 | 复盘 |
| --- | --- | --- |
| W02 · Skills 元数据上限 | 无 Wiki | 有 Wiki 组只做了两次 Grep，把限制全文大小的 `MAX_SKILL_BYTES` 当成元数据上限。无 Wiki 组使用两次 Grep 和一次 Read，答出 `MAX_HEADER_BYTES`。 |
| W11 · 在线与离线 token 统计 | 有 Wiki | 无 Wiki 组达到 CLI 费用预算。获胜组使用一次 Wiki 目录和九次源码工具调用，两组工具调用总数同为 10 次。 |
| W12 · 工具 ID 复用与审批 | 有 Wiki | 无 Wiki 组达到费用预算。获胜组从 8 次源码工具调用降到 5 次源码调用，另查了一次 Wiki 目录。 |
| W17 · 截断后的结果指针 | 无 Wiki | 有 Wiki 组用 5 次源码工具调用得出正确事实，JSON 前附带解释导致解析失败。无 Wiki 组用了 8 次，并按规定返回 JSON。 |
| W18 · 恢复时计算剩余工具调用 | 无 Wiki | 有 Wiki 组查目录 1 次、检索 4 次、读 Wiki 3 次，外加源码工具 3 次，随后达到费用预算。无 Wiki 组用源码工具 8 次答对。 |
| W21 · 截止时间变更 | 有 Wiki | 无 Wiki 组用源码工具 15 次后达到费用预算。获胜组仅用源码工具 6 次，未调用 Wiki。 |
| W23 · 上下文折叠变更 | 有 Wiki | 无 Wiki 组达到费用预算。获胜组查了一次 Wiki 目录，使用源码工具 8 次并答对。两组的源码工具调用总数相同。 |
| W25 · 缓存命中字段变更 | 有 Wiki | 无 Wiki 组达到费用预算。获胜组只查了一次 Wiki 检索，另用源码工具 6 次答对。 |

五次独赢都伴随无 Wiki 组耗尽预算。获胜组只有 W25 调用了 Wiki 检索，W11、W12、W23 只看了目录，W21 未调用 Wiki。基线记录有工具次数，缺少调用顺序、检索结果和具体读到的证据，单题的成功原因无法直接归于 Wiki。W18 提供了一个可复测的假设：对已有可搜索线索的任务，尽早转源码可以压缩 Wiki 调用。

## B/C 诊断对照

- **B 组 | Wiki**：使用与原试点相同的任务提示和工具配置。
- **C 组 | Wiki + 决策策略**：在 Claude Code 的系统提示中追加证据选择规则。根据任务中的可定位线索选择源码直查或 Wiki 检索，命中后用源码核对。Wiki 无有效证据时回到源码，并按原题要求输出 JSON。Wiki 搜索次数约束由提示词引导。
- 两组各自发起八次新会话，使用同一份源码、四页 Wiki 快照、模型、预算、评分和只读工具。两组先跑次数各四次。原有 A/B 保留为历史记录。
- 新报告保存工具调用顺序、可观察的工具返回状态和 Wiki 检索命中数。使用基线题的结果用于诊断和回归。正式评估策略增量，需要另用未见过的题目。

在项目根目录运行。

```bash
python3 evals/wiki_strategy.py verify
python3 evals/wiki_strategy.py run --output runs/wiki-strategy-diagnostic
```

如果本轮已经生成报告，使用 `--resume` 继续。供应商中断或模型、MCP 配置异常时，本轮会暂停。当前题的尝试单独保存在中断记录中，恢复时重跑该题两组。

```bash
python3 evals/wiki_strategy.py run --output runs/wiki-strategy-diagnostic --resume
```

## V2 源码核验与收尾策略

V1 的主要回归是源码工具调用从 48 次增加到 62 次，预算停止从 1 题增加到 5 题。V2 按答案字段决定是否继续查证。一次带上下文的 Grep 如果已给出直接证据，就使用命中片段。只有证据缺口才读相关源码行，同一模块的搜索尽量合并。字段齐全时立即按原题格式提交。源码入口不清楚时仍可用 Wiki 定位。

## W21、W23 定向追踪

先用当前 V2 和普通 Wiki 重跑两题。两组的模型、源码、Wiki 和预算仍使用同一配置。W21 先跑 V2，W23 先跑普通 Wiki。

`--trace-source` 为两组记录工具所在模型轮次。Grep 保存搜索词、范围、筛选条件及返回的文件和可用行号，Read 保存请求范围和实际返回的源码行区间。路径相对固定检出目录。报告从结构化工具结果提取这些字段，缺失的结果细节留空。可按固定提交和行号回查源码。

原来的 V2 报告只有工具名、次数和返回状态，对应时段也没有可用的本机会话日志。定向报告先用于判断是否发生重复查询、搜索范围过宽或证据齐备后仍继续查找。确认一种主要原因后，只修改对应行为，再用同样的两题验证。通过后用整批八题检查既定成功数、预算停止和用量门槛。

```bash
python3 evals/wiki_strategy.py run --strategy v2 --task W21 --task W23 --trace-source \
  --output runs/wiki-strategy-v2-focus --resume
```

## 第 5 阶段的 CLI 接入

普通仓库问答可以直接使用 `agent run`。变更影响任务可选择 `--strategy repo-impact-v2`，它会引导模型限定 `grep` 范围，局部 `read_file`，并用 `finish` 提交结论及源码行号。

```bash
python3 -m agent run "评估修改工具耗时字段会影响哪些模块，给出源码行号" \
  --workspace . --strategy repo-impact-v2 --no-bash
```

需要给模型提供 Wiki 工具时，在项目根目录运行上述命令，并追加 `--mcp-config examples/mcp.repo-wiki.json`。配置为当前工作区启动只读 Wiki MCP，注册列表、检索和读页三个工具。

策略名和实际系统提示写入 `run/start`。`resume <run_id>` 沿用日志里的提示和已有的工具证据。C 组的模型实测来自 Claude Code，新 CLI 入口的验证采用可重复的离线模型和实际源码工具，另验证了可选的真实 stdio Wiki 读取。

离线演示的第六节展示从 `grep` 的命中行直接形成最终答案。可以回放该次运行。

```bash
python3 examples/demo.py
python3 -m agent --runs examples/_demo/runs replay repo-impact --events
```
