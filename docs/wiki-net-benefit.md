# Wiki 净收益试点评测

本实验比较 Claude Code 在可查询和不可查询 Wiki 时的任务交付结果。40 道任务各跑两组，包含单文件定位、跨模块追踪、变更影响分析及修复各 10 道。

## 预先固定的设置

- 源码固定在 `6dda36907aa1825c90d090b14fdab0f69fe22879`。题目与标准答案保存在 `evals/wiki_net_cases.py`。独立会话的源码工作目录不包含题目文件、Wiki 页面或项目凭据。
- 两组使用同一模型、工具和预算。模型调用顺序随机，但四类任务中先跑有 Wiki 与先跑无 Wiki 的次数各为五次。每次调用的超时为 120 秒，沿用第四周问答与修复各自的轮次及 CLI 预算。
- 有 Wiki 组使用项目 `.env` 对应的真实模型生成四张项目 Wiki 页。生成时只提供固定版本的源码，保留页面及来源哈希。修复任务的 Wiki 代表故障发生前最近一次正常发布的快照。两个模型会话从同样的故障代码开始，各自提交补丁。
- 30 道问答均需通过事实字段和结构校验。另报告独立的事实诊断和格式合格数。人工复核可使用打乱顺序、隐藏组别的 `blind-review.json`。10 道修复题须通过定向测试、全量测试和改动范围检查。修复后的验收测试由脚本独立执行。
- 所有分配的任务进入主指标。超时、预算耗尽与 CLI 失败计入失败。两组模型版本不同、MCP 配置错误或评分器异常视为实验条件故障，结果不用于判定门槛。耗时含失败尝试的 CLI 时长，独立评分耗时单列于评测流程之外。

## 门槛与费用

| 路径 | 任务成功数差异 | 有 Wiki 组每次成功成本 | 有 Wiki 组 P90 |
| --- | --- | --- | --- |
| 质量收益 | 净多完成至少 4 项 | 最多增加 10% | 最多增加 10% |
| 效率收益 | 成功数持平 | 至少降低 15% | 最多增加 10% |

每次成功成本的分子含该组所有尝试的实际费用。有 Wiki 组再加本轮生成与更新的实际费用，本试点按 40 道任务承担完整的一次生成费。试点冻结期间无计划更新，生成阶段的付费重试也要计入实际账单。Claude CLI 估算费用和 API token 用于诊断，账单缺失时保留成本未核实状态。成本比与耗时比用未四舍五入的数值比较。

`report.json` 逐条保留结果，并给出分组成功数、仅一组成功的任务数及配对分层 bootstrap 95% 区间。区间针对这批任务的差值估计。达到门槛后，用新的独立任务复验。

## 运行

在仓库根目录运行。实测沿用 Claude Code 的授权配置及项目 `.env`。

```bash
python3 evals/wiki_net.py verify
python3 evals/wiki_net.py run --output runs/wiki-net-live
```

正式运行按任务依次发起 80 次独立会话并保存每个结果，每次运行的 Wiki 构建另计。终端中断后可继续现有目录和已保存的尝试。

```bash
python3 evals/wiki_net.py run --output runs/wiki-net-live --resume
python3 evals/wiki_net.py report --output runs/wiki-net-live
```

从供应商用量明细核对本轮两组和建 Wiki 的费用后，将同一币种的三笔合计写入本地 JSON。字段名为 `currency`、`source`、`without_wiki`、`with_wiki`、`wiki_generation_and_updates`。问答与修复都汇入对应组，不把实验前置探测混入任一组；供应商明细若只能提供两组合计，则成本门槛保持未核实。

```bash
python3 evals/wiki_net.py report --output runs/wiki-net-live \
  --billing runs/wiki-net-live/billing.json
```

## 第一次实测与补测

2026 年 11 月 26 日首次实测走到了 40 对任务的末尾。前 19 对通过评测配置检查，
后 21 对的两组均收到了 Claude CLI 的 `<synthetic>` 错误标记。
旧评分器把标记记为模型切换，原始报告判定为实验条件异常。报告没有保存供应商错误详情，
因此本轮无法判定具体服务端原因。

在中断前的 19 对中，两组各通过 15 题。有 Wiki 组在两道跨模块变更影响题上通过，而无 Wiki 组耗尽预算。
有 Wiki 组在另外两道题中分别填错元数据上限字段和在 JSON 前加入附文。
样本覆盖与完整的预定 40 题有差异，不能据此判定 Wiki 净收益。

补测只替换两组都遭遇该 CLI 错误的任务。19 对有效尝试、原模型设置、题目顺序和四页 Wiki 快照继续使用。
恢复报告记录原始报告哈希及补测题号。供应商中断若再次发生，评测在当前题暂停，
保留该题当次的记录，同一题从两组一起开始恢复。汇总补测的实际账单时，把服务中断及恢复产生的费用按组计入。

```bash
python3 evals/wiki_net.py run \
  --recover-from runs/wiki-net-live --output runs/wiki-net-recovery
```

补测若暂停，可在恢复模型连接后对 `runs/wiki-net-recovery` 使用 `--resume`。

## 完整试点结果

2026 年 11 月 26 日补测完成。原来的 19 对加补测的 21 对，覆盖同一固定版本的全部 40 题。
执行模型为 `deepseek-v4-pro`，四页 Wiki 由 `deepseek-chat` 生成。原定任务、顺序、预算和 Wiki 页面哈希均通过核对。
超时和预算耗尽计入失败。

| 指标 | 无 Wiki | 有 Wiki |
| --- | ---: | ---: |
| 端到端成功 | 28/40（70%） | 30/40（75%） |
| 单文件定位 | 10/10 | 9/10 |
| 跨模块追踪 | 7/10 | 7/10 |
| 变更影响分析 | 3/10 | 6/10 |
| 修复 | 8/10 | 8/10 |
| 预算耗尽 | 10 | 6 |
| 超时 | 1 | 2 |
| 中位耗时 | 22.82 秒 | 18.42 秒 |
| P90 耗时 | 54.78 秒 | 55.13 秒 |

有 Wiki 组独赢 5 题，无 Wiki 组独赢 3 题。净胜 2 题，成功率的配对差值为 +5 个百分点，
分层 bootstrap 95% 区间为 −7.5 到 +17.5 个百分点。P90 增加 0.64%，在 10% 的门槛内。
**本轮未达到预设净收益门槛**。净胜数少于质量路径要求的 4 题，成功数也未形成效率路径要求的持平。
结果支持继续检验变更影响分析这个场景，样本量为 10 题。

38 个两组均有用量记录的配对，无 Wiki 组共 1,206,824 token，有 Wiki 组共 1,273,215 token，
有 Wiki 组多 5.50%。供应商实际账单仍缺失，每次成功任务的实际费用保留未核实状态。
